# UCP conformance suite contract

What the official [UCP conformance suite](https://github.com/Universal-Commerce-Protocol/conformance) (repo at 016ecbc, ucp-sdk 0.4.6, spec 2026-04-08) expects from a merchant server, derived from reading conftest.py, integration_test_utils.py, every test file and the flower_shop test data. Wire payloads were captured from ucp-sdk 0.4.6 directly. Written on 2026-09-17 while preparing the examples/flower_shop conformance target.

## Setup and what the suite hosts

**Toolchain.** pyproject pins `ucp-sdk==0.4.6`, `requires-python >=3.10`, CI uses uv + Python 3.12 and checks out python-sdk at tag `v2026-04-08-6`. `[tool.uv.sources]` points ucp-sdk at a sibling `../python-sdk` editable checkout, so plain `uv sync` needs that checkout. `uv sync --no-sources` + `uv run --no-sources ...` installs 0.4.6 from PyPI and works (verified). All payload shapes follow spec release 2026-04-08. `test_discovery_urls` is `@unittest.skip`, so spec/schema URLs never have to resolve.

**Launch.** Flags live in integration_test_utils.py (absl): `--server_url` (default env `SERVER_URL`), `--simulation_secret` (default env `SIMULATION_SECRET`, else a random uuid, so it must be set on both sides), `--mock_webhook_port` 8284, `--mock_agent_port` 8285, `--verbose_http`, `--conformance_input` default `test_data/flower_shop/conformance_input.json`, `--fixture_config` default `test_data/flower_shop/test_fixtures.json`, `--test_data_dir` default `test_data/flower_shop`. Paths are relative, so run from the conformance dir. conftest.py calls `FLAGS(["pytest"])`, which means under `pytest` only env vars and flag defaults apply. The README's `uv run pytest --conformance_input=...` fails with "unrecognized arguments" (verified). To override flags you must run files individually: `uv run --no-sources some_test.py --server_url=... --simulation_secret=... --conformance_input=...`, which is what CI does in a loop over `*_test.py`. 77 tests total (`pytest --collect-only`).

**conformance_input.json (flower_shop defaults):** `ucp_version` "2026-04-08"; `required_capabilities` ["dev.ucp.shopping.checkout","dev.ucp.shopping.order","dev.ucp.shopping.discount","dev.ucp.shopping.fulfillment","dev.ucp.shopping.buyer_consent"]; `currency` "USD"; `items` [{"id":"bouquet_roses","title":"Red Rose","price":3500}]; `out_of_stock_item` {"id":"gardenias"}; `non_existent_item` {"id":"pink_wumpus"}. Missing file → all defaults (same values, price 3500, sku from items[0] else "item_1").

**test_fixtures.json (flower_shop):** `test_fixtures.valid_item` {sku "bouquet_roses", expected_price 35.0 (major units → 3500), quantity 1}; `valid_discount_code` "10OFF" / `expected_discount_percentage` 10.0; `valid_discount_code_2` "WELCOME20" / 20.0; `valid_fixed_discount_code` "FIXED500" / `expected_fixed_discount_reduction` 5.0 (→ 500); `known_customer` {full_name "John Doe", email "john.doe@example.com", addresses [123 Main St / Springfield / IL / 62704 / US, 456 Oak Ave / Metropolis / NY / 10012 / US]}; `known_customer_without_address` {"Jane Doe","jane.doe@example.com"}; `free_shipping_min_subtotal` 100.0 (→ 10000); `free_shipping_item_sku` "bouquet_roses"; `dynamic_fulfillment.domestic` {destination 123 Main St Springfield IL 62704 US, expected_option_id "exp-ship-us"}; `dynamic_fulfillment.international` {25 King St W, Toronto, ON, M5V 2H1, CA, expected_option_id "exp-ship-intl"}; `shipping_locations.domestic_destination` {street "123 Market St", city "San Francisco", state "CA", postal_code "94105", country "US"}. Fallback discount code when nothing configured is "SPRING20"; optional keys absent → the corresponding tests skip.

**CSV data the suite itself reads:** `payment_instruments.csv` (instrument for complete payloads) and `addresses.csv` (addr_1 for billing address and for order_test destinations). If the CSVs fail to load it silently falls back to a hardcoded instr_1 and a "123 Main St, Anytown CA 12345" billing address.

**Mock agent profile server** (started in every test's setUp, port 8285, host 0.0.0.0): `GET /profiles/shopping-agent.json` returns, with `{ucp_version}` and `{webhook_port}` substituted:
```json
{"ucp":{"version":"2026-04-08","capabilities":{"dev.ucp.shopping.order":[{"name":"dev.ucp.shopping.order","version":"2026-04-08","spec":"https://ucp.dev/2026-04-08/specification/order/","schema":"https://ucp.dev/2026-04-08/schemas/shopping/order.json","config":{"webhook_url":"http://localhost:8284/webhooks/partners/test_partner/events/order"}}]}}}
```
plus `GET /healthz` → `{"status":"ok"}`. Every request the suite sends carries `UCP-Agent: profile="http://localhost:8285/profiles/shopping-agent.json"`. The merchant is expected to fetch that URL and read `ucp.capabilities["dev.ucp.shopping.order"][0].config.webhook_url`. When it fetches (create vs complete) is not asserted. The profile server is up during every test, but the webhook receiver is only up during webhook tests.

**Mock webhook receiver** (only in webhook_test.py and webhook_structure_test.py setUp, port 8284): `POST /webhooks/partners/{partner_id}/events/order` records raw body, parsed JSON, headers; responds `{"status":"ok"}` 200, or 500 `{"status":"retry"}` for the first `failures_before_success` deliveries. `GET /healthz`. In all other tests port 8284 is closed, so merchant deliveries must be async, fail quietly, never delay the complete response, and retries must be bounded.

**Simulation endpoint (SIMULATION_SECRET).** `POST {SERVER_URL}/testing/simulate-shipping/{order_id}` on the base URL (not the shopping endpoint), with the normal headers plus `Simulation-Secret: <secret>`. simulation_url_security_test asserts: header missing → 403; wrong value ("for-sure-incorrect-secret") → 403; correct → 200. Body is not asserted. Effect required by webhook tests: append a fulfillment event with `type: "shipped"` to the order and deliver the full order entity to the webhook URL again. webhook_structure_test skips the update-event test on 403 (secret mismatch) or 404/405 (path missing).

## Endpoint contract

**Common request conventions.** Headers on every call: `UCP-Agent: profile="http://localhost:8285/profiles/shopping-agent.json"`, `request-signature: test` (literal, never valid; must not be rejected), `idempotency-key: <uuid4>`, `request-id: <uuid4>`. JSON bodies via httpx `json=`, so `Content-Type: application/json`. GET and cancel have no body and no Content-Type (`Content-Length: 0`); don't 415. The shopping base URL comes from discovery `services["dev.ucp.shopping"][0].endpoint`, used as an absolute URL (httpx ignores `base_url` for absolute URLs, verified), so it must be absolute and reachable from the test runner. Paths appended: `/checkout-sessions`, `/checkout-sessions/{id}`, `/checkout-sessions/{id}/complete`, `/checkout-sessions/{id}/cancel`, `/orders/{id}`. Every request model is `extra="allow"` and the suite ships response-only fields in requests (see payloads), so the server must ignore unknown keys everywhere, including `groups[].options[].totals` echoed back from its own responses.

**GET /.well-known/ucp** (base URL, no special headers) → 200, body `{"ucp": {...}}`. Inner object validated by `BusinessSchema`: required `version` (must equal conformance `ucp_version` and match `^\d{4}-\d{2}-\d{2}$`), `services` (dict keyed by reverse-DNS → list), `payment_handlers` (dict keyed by reverse-DNS → list; may be `{}` but if present each handler needs non-empty `id` and `version` YYYY-MM-DD). `capabilities` dict keyed by reverse-DNS names (pattern `^[a-z][a-z0-9]*(?:\.[a-z][a-z0-9_]*)+$`), each entry a list of `{version, spec?, schema?, id?, config?, extends?}`; must contain all five required_capabilities. `services["dev.ucp.shopping"][0]` must have `transport: "rest"`, `version` == ucp_version, `endpoint` absolute URL (AnyUrl, required for rest in BusinessSchema). discount_test / fulfillment_structure_test / webhook_structure_test each re-read discovery and skip if their capability key is absent.

**POST {endpoint}/checkout-sessions** → 200 or 201 with a full Checkout. Exact default body (item, price and destination from fixtures; `id` random uuid per call):
```json
{"line_items":[{"item":{"id":"bouquet_roses","price":3500},"quantity":1,"id":"line_item_123","totals":[]}],
 "payment":{"instruments":[],"handlers":[{"version":"2026-04-08","spec":"https://example.com/spec","id":"google_pay","config":{},"name":"google.pay","config_schema":"https://example.com/schema","instrument_schemas":["https://example.com/instrument_schema"]}]},
 "id":"<uuid4>","currency":"USD",
 "fulfillment":{"methods":[{"type":"shipping","line_item_ids":["line_item_123"],
   "destinations":[{"street_address":"123 Market St","address_country":"US","postal_code":"94105","id":"dest_1","locality":"San Francisco","region":"CA"}],
   "selected_destination_id":"dest_1",
   "groups":[{"selected_option_id":"std-ship","id":"group_1","line_item_ids":["line_item_123"]}],"id":"method_1"}]},
 "status":"incomplete","ucp":{"version":"2026-04-08"},"totals":[],"links":[]}
```
With `select_fulfillment=False` the `fulfillment` key is absent. Buyer variants: `{"email":"conformance-test-buyer@example.com","name":"Conformance Test Buyer"}`, `{"fullName":"John Doe","email":"john.doe@example.com"}` (known customer; `fullName`/`name` are unrecognized extras, match customers by email only), `{"fullName":"Unknown Person","email":"unknown-<hex>@example.com"}`, and the consent case `{"first_name":"Consent","last_name":"Tester","email":"consent@example.com","consent":{"marketing":true,"analytics":false,"sale_of_data":false}}`. Note the destination carries `locality`/`region` (not `address_locality`/`address_region`) as extras. The client sends `item.price`; server must price from its catalog. Line item id `line_item_123` and method/group ids are client-supplied and referenced by `line_item_ids`; honor them (or remap consistently). FUL-008 test sends two line items `li_1`,`li_2` with the same SKU and a method with `line_item_ids:["li_1","li_2"]` and destination `{"id":"dest_1","address_country":"US","postal_code":"94105"}` (no groups) → response must have `fulfillment.methods` non-empty; if any method has groups, exactly one group whose `line_item_ids` set equals the method's `line_item_ids` set. Version negotiation (protocol_test): `UCP-Agent: profile="..."; version="2026-04-08"` (the advertised version; note semicolon parameter syntax and an unfetchable profile URL) → 200/201; `profile="..."; version="2099-01-01"` → 422.

**GET {endpoint}/checkout-sessions/{id}** → 200 full Checkout with same `id`.

**PUT {endpoint}/checkout-sessions/{id}** → 200 full recomputed Checkout. Helper body (`update_checkout_session`) always sends `id`, `currency`, `line_items[{id,item:{id},quantity}]`, `payment:{instruments:[...]}` and echoes the previous response's `buyer`, `fulfillment` (whole tree, including `destinations`, `groups[].options[].totals`, `selected_*`) and `discounts` (including the previous `applied[]`) unless overridden. Probe output for a discount update:
```json
{"line_items":[{"id":"li_1","item":{"id":"bouquet_roses"},"quantity":1}],"payment":{"instruments":[]},"id":"chk_1","currency":"USD",
 "fulfillment":{"methods":[{"id":"method_1","type":"shipping","line_item_ids":["li_1"],"destinations":[{"id":"dest_1","address_country":"US","postal_code":"94105"}],"selected_destination_id":"dest_1",
   "groups":[{"id":"group_1","line_item_ids":["li_1"],"options":[{"id":"std-ship","title":"Standard Shipping","totals":[{"type":"total","amount":500}]}],"selected_option_id":"std-ship"}]}]},
 "discounts":{"codes":["10OFF"]}}
```
Hand-built variants also send `line_items[].item.title` and `payment.handlers` (list of instrument dumps) as extras, `buyer` `{email,first_name,last_name,phone_number}`, and fulfillment shapes: method with only `{id,type,line_item_ids}` (no destinations, triggers stored-address injection); method with `destinations:[{...}]` + `selected_destination_id`; method with `selected_destination_id` only (select an injected address, no destinations key); `groups:[{id,line_item_ids,selected_option_id}]` (option selection; note group update without `options`). Update on a canceled or completed checkout → any non-200 (409 recommended). PUT bodies with `id`/`currency` at top level must be accepted.

**POST {endpoint}/checkout-sessions/{id}/cancel** (no body) → 200 full Checkout with `status: "canceled"`. Second cancel with a new key → 200 with the same id and `canceled`, or any 4xx (never 5xx). Cancel on completed → non-200.

**POST {endpoint}/checkout-sessions/{id}/complete** → 200 full Checkout with `status: "completed"` and `order: {"id": ..., "permalink_url": "<absolute URL>"}` (both truthy; `order.label` optional). Default body (`get_valid_payment_payload`, instr_1 + addr_1):
```json
{"payment":{"instruments":[{"id":"instr_1","handler_id":"mock_payment_handler","type":"card","display":{"brand":"Visa","last_digits":"1234"},"credential":{"type":"token","token":"success_token"},
  "billing_address":{"street_address":"123 Main St","address_locality":"Springfield","address_region":"IL","address_country":"US","postal_code":"62704"}}]},"risk_signals":{}}
```
`risk_signals` is an unknown extra. Failing variant uses `id:"instr_fail"`, `last_digits:"0000"`, `token:"fail_token"`. Complete on canceled → non-200; complete again with a new idempotency key after success → non-200. Before completing, `complete_checkout_session` runs `ensure_fulfillment_ready`: GET the checkout; ready means `fulfillment.methods[0].selected_destination_id` truthy and `groups[0].selected_option_id` truthy; otherwise it injects `{"id":"dest_default","street_address":"123 Default St","address_locality":"City","address_region":"State","postal_code":"12345","address_country":"US"}`, selects `destinations[0].id`, then selects `groups[0].options[0].id` by PUTting the whole method dict back. checkout_lifecycle_test's `test_complete_checkout` tolerates a 409 whose text contains "stock".

**GET {endpoint}/orders/{id}** → 200 Order (see shape below) with `id` == order id and `checkout_id` == originating checkout.

**PUT {endpoint}/orders/{id}** → 200 Order. Body is the GET response dumped with `exclude_none`, `by_alias` (so it includes `ucp`, `permalink_url`, `totals`, line items with `quantity:{original?,total,fulfilled}` and `status`), with either `fulfillment.events` appended: `{"id":"evt_<uuid>","occurred_at":"<tz-aware ISO>","type":"shipped","line_items":[{"id":<li.id>,"quantity":<li.quantity.total>}],"tracking_number":"TRACK123","tracking_url":"http://track.me/123","description":"Shipped via FedEx"}` → response `fulfillment.events[0].tracking_number == "TRACK123"`; or `adjustments` appended: `{"id":"adj_<uuid>","type":"refund","occurred_at":...,"status":"pending","totals":[{"type":"total","amount":-500}],"description":"Customer refund request"}` → response `adjustments[0].totals[0].amount == -500` and `type == "refund"`. Must return 422 when `adjustments[].status` is `"INVALID_STATUS"` (that payload also has `"amount": 500` and no `totals`) and when `adjustments` is a dict `{"id":"adj_1","amount":100}` instead of a list. 422 body is not inspected.

**Checkout response shape** (`Checkout` model, all `extra="allow"`): required `ucp` (min `{"version":"2026-04-08"}`; `status` defaults to "success"), `id`, `line_items[]`, `status` ∈ incomplete|requires_escalation|ready_for_complete|complete_in_progress|completed|canceled, `currency`, `totals[]`, `links[]` (may be empty; entries `{type,url:<AnyUrl>,title?}`). Optional but effectively required: `payment: {"instruments": [...]}` must always be present with a list (several tests iterate `checkout_obj.payment.instruments` with no None guard; each instrument needs `id`,`handler_id`,`type`). `line_items[]`: `id`, `item:{id,title,price:int>=0,image_url?:AnyUrl}`, `quantity:int>=1`, `totals:[{type,amount}]` where tests read the `subtotal` and `total` entries (both must equal unit price × quantity), `parent_id?`. `totals[]` (`Totals` validator): exactly one `subtotal` and exactly one `total`; every entry `{type:str non-empty, amount:int (JSON integer, not string/bool), display_text?}`; custom types outside subtotal/items_discount/discount/fulfillment/tax/fee/total require `display_text`; `subtotal`/`fulfillment`/`tax`/`fee` must be >= 0; `discount`/`items_discount` must be < 0 (a zero discount entry fails validation, so omit it). Invariant asserted: `total.amount == sum(amount of every non-total entry)`; `subtotal` == undiscounted item sum; `test_fulfillment_flow` asserts `total == price + selected option's total` exactly, so no tax/fee lines unless zero (and zero-amount tax is allowed but pointless). `buyer` `{first_name?,last_name?,email?,phone_number?,consent?:{marketing,analytics,preferences,sale_of_data}}`. `messages[]` entries: error `{type:"error",code,content,severity∈recoverable|requires_buyer_input|requires_buyer_review|unrecoverable,path?,content_type?}`, warning `{type:"warning",code,content,...}`, info `{type:"info",content,code?}`. `expires_at`/`continue_url` optional (tz-aware datetime / AnyUrl). `fulfillment` and `discounts` are extensions read as raw dicts (`model_extra`): `fulfillment.methods[]` `{id,type:"shipping"|"pickup",line_item_ids[],destinations?[{id,street_address?,address_locality?,address_region?,postal_code?,address_country?,...}],selected_destination_id?,groups?[{id,line_item_ids[],options?[{id,title,totals[{type,amount}],description?,carrier?}],selected_option_id?}]}`. Tests also tolerate `fulfillment.root.methods` but plain `fulfillment.methods` is what to emit. `discounts` `{codes?[],applied?[{code?,title (required),amount:int>=0 (positive magnitude),allocations?[{path,amount}],automatic?}]}`.

**Order response shape** (`Order` model): required `ucp`, `id`, `checkout_id`, `permalink_url` (AnyUrl), `line_items[]` (`{id,item:{id,title,price},quantity:{total:int>=0,fulfilled:int>=0,original?},totals:[...],status∈processing|partial|fulfilled|removed,parent_id?}`), `fulfillment:{expectations?[],events?[]}`, `currency`, `totals` (same one-subtotal/one-total rule). `expectations[]`: `{id,line_items[{id,quantity>=1}],method_type∈shipping|pickup|digital,destination:{postal address fields},description?,fulfillable_on?}`; `expectations[0].description` must equal the selected fulfillment option's `title` exactly, and `expectations[0].destination` must carry the selected destination's `street_address`,`address_locality`,`address_region`,`postal_code`,`address_country`. `events[]`: `{id,occurred_at (tz-aware),type,line_items[{id,quantity>=1}],tracking_number?,tracking_url?,carrier?,description?}`. `adjustments?[]`: `{id,type,occurred_at,status∈pending|completed|failed,line_items?,totals?,description?}`. `label?`, `messages?`, `attribution?`.

**Idempotency (idempotency_test.py).** Header `idempotency-key`. Create: same key + identical body twice → identical status code and identical JSON body (so return the stored response verbatim, including any timestamps); same key + body with `currency:"EUR"` → 409. Update: same key + same body → 200 identical body; same key + `quantity` 2→3 → 409. Complete: same key replay → 200 identical body even though the checkout is now completed (key lookup must precede the state check); same key + `credential.token:"different_token"` → 409. Cancel: same key replay → 200 identical body. The second create request reuses the same client-generated checkout `id` in the body.

**Business/validation errors (validation_test.py).** Two accepted postures. 4xx: body is either UCP `ErrorResponse` `{"ucp":{"version":...,"status":"error"},"messages":[{"type":"error","code":...,"content":...,"severity":...}],"continue_url"?}` (model is `extra="forbid"`, so no other top-level keys, e.g. no `id`/`status`; at least one message with `type:"error"` whose `content` contains the substring, case-insensitive) or a legacy `{"detail": "...substring..."}`; if the body is not JSON the substring must appear in raw text. 2xx in-band: `messages[]` must contain at least one `type:"error"` entry with all of `type`,`code`,`content`,`severity` non-empty and at least one `code` in the accepted set; if the body has no `id`, `ucp.status` must be `"error"`; if it has an `id`, `ucp.status` must be absent or `"success"`, `status` must be a non-completed enum value, and `order` must be absent. Cases: create with `gardenias` (stock 0) → substring "stock" / codes {out_of_stock, item_unavailable} (used by both test_out_of_stock and test_structured_error_messages); create with `pink_wumpus` → "not found" / {not_found, item_unavailable}; complete with `fail_token` (checkout created with `payment.handlers: []`) → "payment" / {payment_failed}; complete a checkout created without any fulfillment → "fulfillment" / {missing, field_required}; PUT quantity 10001 on bouquet_roses (stock 1000) → same stock posture OR 200 with a `type:"warning"`,`code:"quantity_adjusted"` message, no error messages, and every `line_items[].quantity` an int < 10001. invalid_input_test: unknown code `INVALID_CODE_123` on PUT → 200 and no `totals` entry of type `discount`; the two order 422 cases above. Version mismatch → 422.

**Discounts (business_logic_test.py, discount_test.py, totals_test.py).** Input `discounts.codes[]` on PUT; a submitted set replaces the previous set; `[]` clears (no `discount` totals entry and `applied` empty/absent); unknown codes are silently dropped (200), never an error; matching is case-insensitive ("10off" must apply; the echoed `applied[].code` is compared uppercased); client-supplied `discounts.applied` must be ignored (an injected `{"code":"__INJECT__","amount":10000000,...}` alongside a valid code must yield the same total as the valid code alone). Output: a `totals` entry with `type:"discount"` (this literal, negative; one entry is simplest, one per code also passes since business_logic sums all discount entries and discount_test reads the first; `items_discount` would fail discount_test and invalid_input_test, and its magnitude is included in business_logic's sum so don't emit both), `subtotal` stays 3500, `total` = 3500 − discount (fulfillment not selected in these tests). Expected magnitudes: 10OFF → 350; FIXED500 → 500 and `applied[FIXED500].amount == 500`; 10OFF+WELCOME20 → 980 (sequential, 350 + round(3150×0.2)) or 1050 (cumulative); 10OFF+INVALID_CODE → 350 with INVALID_CODE absent from `applied`; `applied[]` must list each submitted valid code with `title` and `amount`; if `allocations` are emitted their amounts must sum to `amount` (skips otherwise). totals_test applies 10OFF with fulfillment selected and only checks the sign.

**Fulfillment (fulfillment_test.py, fulfillment_structure_test.py, order_test.py).** After a PUT that supplies a destination + `selected_destination_id`, the response must contain `groups[0].options[]`, each `{id,title,totals:[...,{type:"total",amount}]}`; sibling titles non-empty and distinct. Destinations arrive in several shapes: full (`full_name` extra + all five address fields), partial (`address_country`+`postal_code` only, or plus `street_address`), the SF fixture with `locality`/`region` extras, `"id": ""` (empty string, reuse test), and the CA address `{"address_country":"CA","postal_code":"M5V 2H1","street_address":"Webhook St"}`. Expected behaviour: US destination → options include `exp-ship-us`; CA destination → options include `exp-ship-intl`; switching destinations in successive PUTs must recompute options for the newly selected one. Free shipping: a zero-cost option (`totals` has `total` amount 0; id/title free) must be offered when subtotal > 10000 (test orders quantity 3 → 10500) and when the item is `bouquet_roses` (promo_2), which is also the default test item, so nearly every checkout qualifies; test_fulfillment_flow picks `options[0]` and asserts `total == 3500 + that option's total`, so ordering is free. Stored addresses: known buyer email `john.doe@example.com` + PUT with a method lacking `destinations` → response `destinations` contains both stored addresses (matched by content on the five fields, ids server-assigned); a PUT with `selected_destination_id:<that id>` and no destinations → selection reflected, destinations retained, selected one carries the matching content; a PUT with a new destination for a known buyer → new content present, `selected_destination_id` ∈ {client id, server canonical id}, options generated; resubmitting stored content with `"id": ""` → served under the previously injected id. Unknown email or `jane.doe@example.com` (customer with no addresses) → `destinations` absent or empty. Selection semantics in lifecycle test_update_checkout: PUT replacing destinations with `dest_2` (456 Elm St, Beverly Hills, 90210, US, with `locality`/`region` extras) and `selected_destination_id:"dest_2"`, groups echoing the existing group's id/selected_option_id/line_item_ids → response `selected_destination_id == "dest_2"` and a destination with id `dest_2`, `postal_code` 90210, `street_address` "456 Elm St" (client id kept here). Selected option must flow into the order's `fulfillment.expectations[0].description` (== option `title`) and destination.

**Webhooks (webhook_test.py, webhook_structure_test.py).** On completion, POST the full Order entity (same JSON as GET /orders/{id}: `ucp,id,checkout_id,permalink_url,line_items (non-empty),fulfillment,currency,totals` all non-null) to the profile's `webhook_url`. Poll window is 5 s after complete returns in test_webhook_event_stream and all of webhook_structure_test, but only 2 s (20 × 0.1 s) in test_webhook_order_address_known_customer and test_webhook_order_address_new_address, and those two break on the first recorded event of any kind and then look up `e["payload"]["id"]` without `.get`, so the created-order delivery must be the first thing the receiver sees, must arrive within ~2 s, and every body must carry `id`. Those two tests also select the option with a hardcoded `groups:[{"id":"group_1",...,"selected_option_id":...}]` regardless of the group id the server returned; a PUT naming a group id the server did not generate must still return 200 (ignore or remap it; `ensure_fulfillment_ready` re-selects afterwards if the selection was dropped). Headers required: `Webhook-Id` (unique per event) and `Webhook-Timestamp` (unix seconds, `^\d+$`, between 1e9 and 4e9). After simulate-shipping, deliver the full order again with a `fulfillment.events[]` entry of `type:"shipped"` within 5 s; `checkout_id` on every delivery must equal the checkout. Retry: when the receiver answers 500 on the first attempt, a retry must land within ~5 s carrying the same `Webhook-Id`, same `Webhook-Timestamp`, and byte-identical parsed payload; then stop after 200. Bound the retry horizon for refused or failed deliveries to a few seconds total. Under pytest the files run alphabetically, so roughly 60 orders complete against a closed port 8284 before the webhook files run; a merchant still retrying those would leak stale deliveries into the receiver, which can consume the single 500 in test_transient_failure_retries_preserve_event_identity (so the real first delivery gets 200 and the test reports "not retried") and can trip the 2 s first-event break above. Address assertions: `fulfillment.expectations[0].destination` must match the selected destination (known-customer injected address, or the CA "Webhook St" address). Signing is all-or-nothing: if any of `UCP-Agent`, `Signature`, `Signature-Input`, `Content-Digest` is present, all four must be, `UCP-Agent` must be `profile="<url ending in /.well-known/ucp>"`, `Content-Digest` must be `sha-256=:<base64>:` over the raw body bytes, and `Signature-Input` must list `"@method" "@authority" "@path" "content-digest" "content-type"` inside its `(...)` (missing `"ucp-agent"` only skips). Sending none of the four skips both signing tests cleanly.

**Payments / AP2 / card / binding.** Discovery must advertise a payment handler group (reverse-DNS key, e.g. one whose handler `id` is `mock_payment_handler`, with `version`); nothing checks that instrument `handler_id` matches, but all instruments use `handler_id: "mock_payment_handler"`. Complete must accept: token credential `{"type":"token","token":"success_token"}` (success) and `"fail_token"` (payment failure posture above); a raw card credential `{"type":"card","card_number_type":"fpan","number":"4242424242424242","expiry_month":12,"expiry_year":2030,"cvc":"123","name":"John Doe"}` with instrument `id:"instr_card"`, display Visa/1111 → 200 completed; a token credential with `"binding":{"checkout_id":<id>,"identity":{"access_token":"user_access_token"}}` → 200 completed; and an AP2 body `{"payment":{...instr_1...},"risk_signals":{},"ap2":{...entire checkout response...,"checkout_mandate":"header.payload.signature~kb_signature"}}` → 200 completed (no signature verification is asserted). Display brand may be "visa" or "Visa". Create requests carry `payment.handlers` with a fake `google_pay` handler; ignore it.
